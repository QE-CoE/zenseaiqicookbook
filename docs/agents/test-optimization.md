# Test Optimization

> **Suite Optimisation Agent** — finds redundancy in an existing test suite, merges duplicates, and improves coverage per test.

## What it does

Test Optimization addresses the way test suites accumulate. Every release adds cases, almost none are ever removed, and after a few years a suite carries substantial duplication that nobody dares delete because nobody is certain what each test uniquely covers. The cost is recurring rather than one-off: every redundant test consumes runtime on every execution and needs maintenance whenever the application changes. Its input is an existing suite, either generated by CaseGeni or imported from your current estate. It identifies tests that duplicate one another's coverage in substance rather than in wording, proposes merges that consolidate duplicate sets into a single stronger test, assesses what the suite covers and leaves untested, and reports how much smaller the suite becomes and what is retained. Testers and automation engineers use it when rationalising an inherited regression pack, or after a period of heavy feature work when duplication grows fastest. Well-tagged suites produce sharper clustering, since the tags CaseGeni generates feed the analysis directly. Merge proposals are recommendations rather than automatic edits and should be reviewed, because two apparently redundant tests occasionally differ in a precondition that matters. The important outcome is not simply a smaller suite but the coverage evidence supporting each reduction, which is what allows a QA lead to actually approve the deletions. For engineering the benefit is shorter cycles and less maintenance; for delivery managers it replaces "we have four thousand tests" with a defensible statement of what is covered. It sits alongside the other Quality Intelligence agents and is typically run periodically rather than on every change.

Point Test Optimization at a test suite and it assesses the set as a whole rather than case by case.

**What you give it:** an existing test suite — generated by [CaseGeni](casegeni.md) or imported from your current estate.

**What you get back:**

| Output | Description |
|---|---|
| **Redundancy analysis** | Tests that duplicate each other's coverage, in substance rather than wording |
| **Merge proposals** | Duplicate sets consolidated into a single stronger test |
| **Coverage assessment** | What the suite covers, and what it leaves untested |
| **Reduction summary** | How much smaller the suite becomes, and what is retained |

## Why it matters

Test suites accumulate. Every release adds cases, few are ever removed, and after a few years a suite contains substantial duplication that nobody can safely delete because nobody is certain what each test uniquely covers.

The cost is real and recurring: every redundant test consumes execution time on every run, and needs maintenance whenever the application changes.

Typical use:

- **Suite rationalisation** — reduce an inherited regression pack to what actually earns its runtime
- **Execution cost reduction** — fewer tests, same coverage, shorter cycles
- **Maintenance reduction** — every removed duplicate is one less test to fix when a locator changes
- **Coverage clarity** — replace "we have 4,000 tests" with a defensible statement of what is covered

The business outcome is a smaller, faster, cheaper-to-maintain suite with coverage evidence for the reduction — the assurance needed to actually approve the deletions.

## Tips

- **Tags matter.** CaseGeni's `tags[]` field feeds the analysis — a well-tagged suite produces sharper redundancy clustering.
- **Review merges before applying.** Two tests that look redundant sometimes differ in a precondition that matters; the proposals are recommendations, not automatic edits.
- **Re-run after major feature work**, when duplication is introduced fastest.
